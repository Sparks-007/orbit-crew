     1→## Safety invariants
     2→
     3→- Trust check (`src/server/trust.ts`): one checker decides every connected app action, every browser step that can commit (click, key press, choosing an option, ticking a box, drag, upload, accepting a page dialog, a page script with side effects; reads, typing and read-only scripts skip it, and a download aimed at a control instead of a link is checked as a click), and every sign-in or saved-session use before it runs, app reads included (tool discovery with `SEARCH_TOOLS` reads no app content, only connected account names, and skips it), and every change Nod makes to its own schedules, notification settings, the owner's rules, spending limits or memory (forgetting a note, turning memory on or off, clearing it); a scheduled run is checked against its saved owner inputs and later corrections, bound reply proposals, exact complete schedule approval when present, and run time and time zone. Earlier eligible owner messages are background only and cannot grant another action. Every checker receives the same evidence roles. Each correction changes only what the owner addresses; a later restriction removes earlier permission. Definition changes and their exact checked evidence save together under the turn lock with checks for a stale target or owner-input revision. A name, timing, watch or enable approval changes only those fields. A complete schedule instruction approval describes its full future work, targets, timing and limits; hidden scope refuses the question, and one-action approvals never grant recurring work. Required withdrawn or unavailable sources refuse the saved work, never restore an older grant; an owner-written or explicitly approved complete replacement can establish a new instruction. No message-count cap discards permission evidence, and no model summary becomes authority. An event turn is checked against the owner's notification rule, its standing instruction. Saving a note follows the memory rules below, and only a turn started by an owner message can forget a note or clear memory. `NOD_TRUST_MODEL` selects `selected` (the default), `llm` or `decision`. `selected` uses the owner's selected model, or an audio model's visible same-connection text companion, at the lowest reasoning effort, never the model a turn's work runs on. `llm` checks always use a known small model. They prefer the selected connection, then another connected service, and never use the larger chat model as a fallback. Decision mode selects direct TypeSafe Jev 1.14, OpenRouter Jev 1.14, Perplexity Decider 1.2 through OpenRouter, then OpenAI Decisions directly or through OpenRouter. If none is available, it selects the same small LLM before the check starts. A failed lookup blocks the check. A failed or uncertain decision never switches the checker to an LLM. Jev combines native probabilities with a fixed monotonic classifier. Separate owner-only permission, nested-effect and typed time checks support its decisions. Providers are selected before a request and stay fixed for all steps of the check. There is no separate decision-model override. For most approvals, the selected model writes a concise question and action label from the saved action and available target details, and a separate request to that model checks both. For permanent Gmail deletion, the server writes a fixed English question and action label from the verified target without a wording-model request. The checker sees the owner's configured time zone and only their recent messages (for a task, the chat's recent owner messages frozen when the task started, never later chat messages, plus the owner messages addressed to that task), the owner messages in its turn chain (the request and every answer to Nod's questions), and the message they answered (the one the owner replied to, or else the latest assistant message in that channel before it; a task's check sees it only when it is that task's own message), which shows what the reply answers and never proves what the owner saw or approved (a first task the owner tapped and the label of an approval card's button are Nod's wording, so they never count as their message), or for a scheduled run the instruction that created its schedule, followed by each later owner message through which Nod changed its prompt (up to ten; one more, a change from work without an owner message, or the owner's own edit replaces them all), and the run's time and time zone, plus as `scheduleContext` up to five owner messages from the same conversation in the 24 hours before the creating message, frozen when the schedule is created (none withdrawn, over 4,000 characters, a confirmation answer or a tapped task card), which only show what the instruction refers to and are never quoted or counted as permission, so the server accepts a schedule quote only from the instruction and its changes, or for work Nod starts on its own the current notification rule, plus the action's arguments as Nod sends them, never tool results; it always sees the whole request and the whole reply. A withdrawn turn's owner messages never count, not even in the turn chain, and when the message a reply answered was posted by a withdrawn turn the checker sees no answered message rather than an older one, so the owner authorizes that work again by asking again. Every check, in every kind of work, also sees the owner's rules (`preferences.rules`): their lasting words on what Nod may do without asking or must ask about first. Only then does the checker prompt gain its rules paragraph, so owners without rules get the same prompt as before. A rule to ask first, or not to act, makes the action ask even when other owner words cover it; a rule to go ahead counts as owner words for what it says and never covers Nod's own settings. The checker names a rule as the reason it asks only when the owner has rules. To run a non-read action the checker must quote, word for word, the owner words that allow it (a message it was shown, the schedule instruction, the notification rule or the owner's rules), or say "read"; opening a local file (`LOCAL_FILES_READ`, `LOCAL_FILES_IMPORT`) never counts as a read, like a sign-in; the server checks the quote appears in what it showed and otherwise asks, records the basis and a short target with each app action, committed browser step, change to Nod's own settings and Vault use, and Usage shows the quoted words while their message still exists. A rule change Nod makes shows the checker the current rules, so the owner's words must cover anything it adds; the owner's own edit in Usage needs no check. Work Nod starts on its own (event turns, activity checks included) gives it no owner words beyond that rule and the owner's rules, neither of which covers Nod's own settings, never the event, and a resume that traces back to no owner message, schedule or event gives it only the owner's rules. A notification rule change shows the checker the current rule, so the owner's words must cover anything it adds. It runs reads, drafts and actions the owner's words ask for, where words that ask for an outcome (buy this there, move that meeting and tell its people) cover the steps it needs on the target they name up to and including the commitment they name, and nothing past it; a general request to solve a problem or a supplied document does not choose an outside commitment, and a short reply inherits only a concrete proposed action or outcome on its target, never advice listing possibilities or a general offer to help; a browser step whose effect its control leaves unclear runs only inside such an outcome on that website, never for a question, lookup or summary, and only when its worst plausible effect stays within it, and cookie-banner choices count as reading, since they stay in Nod's own browser. Anything else waits for the owned yes/no confirmation, and a failed check asks; in scheduled and event work, a check that fails or gives no verifiable basis refuses the action with the reason instead of asking, while an answer that doesn't allow the action, uncertain decisions included, still asks. No stored list of recipients or past confirmations skips the check. Every confirmation is bound to the exact action and arguments and stays open while its turn waits; a turn, subagents included, has at most one open confirmation, approvals refuse a second, and no app or memory call issued after one that asks runs; a reply answers only the confirmation it was read against, never one asked while Nod was reading it, and a reply to one that is no longer pending is an ordinary message. The checker reads the owner's reply to a confirmation on its own, without the question or the action, and only a reply it reads as an unconditional yes approves. In web and desktop the confirmation is a card whose controls answer that approval by its ID without the reply check: the action approves and the refusal choice declines, the click's label is never shown to the checker, memory or the language context, and a click that names another approval, or one no longer pending or whose turn ended, is refused and changes nothing. A reply it can't read leaves the confirmation open; any other reply closes it without running, and a direct reply to a background session's confirmation continues that session. Only questions are recorded. Confirmed actions run once; failed or interrupted ones become uncertain and are never re-run, and the resumed turn continues with the reason, as it does when a confirmed action can no longer run. When Stop or a failure ends that resumed turn first, each later turn of its session is told whether the approved action ran, may have run or did not run, until a turn of that session succeeds or waits for the owner. A recorded question fences its exact action for the rest of that request, even when the checker would now run it: once done, a repeat returns the recorded result; while pending, declined or uncertain, a repeat is refused; an expired one never ran and fences nothing. A browser step is described by agent-browser's own ref label or the accessibility tree, plus the method and address of the form a click or Enter would send (for Enter in a field, through the form's default button), read from that element's form in an isolated world, never page parsing, or unknown when the browser can't inspect the control or same-label controls send different forms; a confirmed step replays once only while the browser is on the same page, its refs still exist and the form it sends is unchanged, otherwise it does not run; subagents refuse steps that would ask. For a browser question, the writer and its separate review can read the page's visible text as target context. They do not display the page dump. The trust checker never sees page text.
     4→- App, browser, web and codemode results that the model receives directly, confirmed-action results and failures, and connected-app event data (the whole event, with secret-named keys removed and email that gives account access hidden: each mail-shaped record is checked on its own by a decision model, or else the connection's smaller model, from its sender, subject, HTML link destinations and the start and end of its text; no decision is reused from an earlier read; a failed check hides it; downloaded mail files are not checked) reach Pi inside one `untrusted_tool_result` block with a data-not-instructions notice; tags inside the content are neutralised. Errors reach Pi unwrapped. Calls made by codemode scripts stay raw. A connected MCP server's tools also run as their own deferred Pi tools (`mcp__<server>__<tool>`), directly or from codemode, through the same trust check, ordering and wrapping as `apps`; each server's own instructions reach Pi inside one untrusted block. `usage_get` returns Nod's own records inside one untrusted block too, because action targets carry page text such as control labels. Nod's own confirmation notice is the only app result left unwrapped. Nothing scans content for injection phrases; the server limits what fooled text can do.
     5→- Vault and sign-in: `sign_in` never returns a saved value. The one trust checker decides each sign-in and saved-session use from the owner's words (a sign-in the owner completes in the private form needs no check, because entering it is their consent); otherwise the owner's yes, bound to the exact origin and item, covers the rest of that task. A domain mention does not grant consent. The server claims a durable use before browser work. Pi selects the fields and submit control; the provider checks actual frame origins, enters and submits privately, then keeps the live page for Pi to inspect, and a saved-login entry returns that page inside its untrusted result. Known secret values (passwords, codes, card numbers and security codes, not usernames or the cardholder name) are removed from tool output and masked in screenshots. A saved login's authenticator key never leaves the server: when a page asks for a code without `emailCode`, the server generates the current code and enters it like any code, after the same trust check as that login, only for the login this task signed in with (without one, the login Pi names or the only keyed login for the origin), once per sign-in. 1Password logins reach Vault only when the owner picks one in the private form: the 1Password SDK runs in a separate helper process (on macOS the Electron Plugin helper, the only Nod process allowed to load 1Password's library), never in the server; it lists only the logins 1Password would fill on the request's exact origin and re-checks the picked item, and Nod saves an encrypted copy that then works like any saved login. Native side-effect checks permit read-only JavaScript without a reload; a document changed by Pi JavaScript requires a reload before entry. All normal Pi tools work after submission, except that page scripts pause on a document where Nod filled a private value until it reloads or navigates, and a reload of a page reached by a form POST, or whose navigation Nod can't read, re-opens its address with a GET rather than resubmitting. Failed entry keeps the observation lock until the filled document changes. Event turns carry only the notification rule, so their sign-ins and saved-session uses ask the owner unless the rule needs that website and, for a saved session, the website it belongs to; every schedule fire, event and subagent starts in its own fresh browser. Secure forms and payment requests bind owner, turn and origin, stay open while their turn waits, and close when a newer request or a newer turn starts in their session (a chat message never closes a background session's form); the waiting turn resumes in the transaction that records the entry. The server and destination website are trusted with submitted values; output redaction does not contain every transformation a website can make.
     6→- Pi reads the page from the agent-browser snapshot and chooses login methods and fields. Do not add page-parsing scripts, snapshot regexes or field checks around the browser; leave the page to Pi, the model and agent-browser. Pi can run page JavaScript with browser evaluate. Tool output replaces known secret values. Keep site-specific cases in regression fixtures. Two exceptions: when a browser step asks the owner, the server reads the bound page's `document.body.innerText` with a read-only script for the confirmation question, which never reaches the checker; and before a click or Enter, the server reads the method and address of the form that the exact target element would send, through the form's own properties in an isolated world, for the checker.
     7→- Before choosing a login method, check saved account metadata. Reuse a uniquely applicable login, which selects the password method because a saved login is a username and password, or the method the user chose. If the method remains ambiguous, offer the observed controls through `sign_in` with `kind: 'method'` so the owner chooses in the private panel. Ask in chat when the matching account remains ambiguous.
     8→- Payments: `pay` binds one request to the shop, checkout document, actual card-field origins, submit control, amount, currency and selected card revision. The owner approves in Nod web or desktop with the card's security code, which Nod never stores. A chat-app task uses the desktop private form and resumes in its original channel. Private URLs and payment codes never pass through chat apps. The claim locks and reads the approved revision on an active turn. The provider uses field-bound private entry and submission, then keeps the live page and removes known secret values from observations. A durable use never runs twice; interrupted work is uncertain. Usage records card submitted, not paid. A payment from an event turn needs the owner's approval like any other. Stored PAN use does not enforce settlement at the issuer or establish PCI compliance.
     9→- Secrets in chat: Pi is told never to ask for passwords, codes, card details or API keys in chat and to use `sign_in` or `pay`, which open private entry. Nothing filters the reply text. While a verification request is pending, only a message whose only letters or digits are the code, 4–8 digits 0–9, is the code; any other message with a number of three or more digits that ends it or doesn't follow a letter or digit, in any wording or language, is refused with a request to send the code by itself, so it reaches neither the website nor the model. While a payment request is pending, a card code sent by itself (3–4 digits) or one labeled CVV, CVC or security code is caught. A code sent as a reply to a closed request is refused, and a code by itself or ending a message is refused until ten minutes after a newer turn starts in that session. Other messages and any other secret the owner types reach the model.
    10→- Pi never writes memory text. `memory_learn` works only in work the owner started (chat or a task) with an owner message: the server reads that message, the owner's last 10 messages in its conversation that aren't withdrawn and any older owner messages Pi names by ID (never a task-card title the owner tapped, a message over 4,000 characters or one with a secret), and only those messages and the memory index reach the memory model, which writes one declarative fact per note and may archive notes they make untrue; the server keeps only notes that quote a cited owner message and hold no secrets, saves them as confirmed and archives instead of deleting. Background memory learning reads only the owner's own user messages (up to 4,000 characters, no attachments, none with a memory-save approval, none withdrawn, never a task-card title the owner tapped), never assistant text or tool results; web content reaches memory only if the user pasted it. Learned entries stay tentative until a second message repeats them, and automatic changes archive active entries instead of deleting them. The archive itself is bounded, and only a user-requested forget deletes a note; when memory is full, the least recently used learned skill the owner hasn't edited is dropped. Sensitive topics (health, religion, politics and similar) are learned in the background only when the owner turns them on, and Pi is told to save them only then or when the owner explicitly asks. One exception: when Gmail connects, a background job reads the owner's own text from recent sent emails (quoted, forwarded and automated mail removed) and saves only their writing style, with no facts, names or quotes, as one capped `preferences` entry labelled "Learned from your sent email" that replaces its earlier version by archiving it. Learned skills are the one kind of memory Nod writes itself: Pi saves or patches one (`skills save`/`patch`) only in work the owner started (chat, a task or a schedule), never from event turns or subagents, and not while saving is off. The server redacts known secrets from each draft, then the memory model rewrites it as a procedure without personal data, as a model's best effort, dropping outside sends the flow didn't need. Skill text reaches Pi as untrusted data, never counts as owner words, and never reaches the trust checker or confirmation formatter.
    11→- Conversation traces: only while the owner's **Share conversation traces** switch is on, each Pi model request and its reply, with the model that actually handled it, except checks of account-access email and the memory, writing-style and skill writers, leaves through `src/server/traces.ts`, which groups a session's requests under a random conversation ID (`thread_id`, LangSmith's thread key) that changes after 30 minutes without a request and on restart, sends no session ID, replaces the other execution IDs, and Nod's IDs inside the content, with keyed hashes that change daily and on restart, replaces the home folder path with `~`, and removes known secrets, the names on the owner's connected app accounts and validated personal identifiers (`src/server/personal-data.ts`; `src/providers/pi/traces.ts` replaces images with `[image]` and drops the owner context, memory tool results and learned-skill reads, keeping only their action) before the n8n Nod Traces workflow forwards it to LangSmith. Traces are pseudonymised, not anonymous: what a conversation says can still identify the owner. Separate decision-model calls are not included. Turning the switch off stops sending at once. Nod never holds a LangSmith key; official desktop builds carry only the workflow's webhook token, from the release secret.
    12→- File previews: artifact HTML renders only as `srcdoc` in an `allow-scripts` iframe without same-origin, behind a no-network CSP placed before the content, and the preview closes if the frame loads another document. Other formats render as text, canvas, React or a script-less sandboxed frame, never as HTML in the app's DOM. HTML, SVG and XML never get a local `blob:` preview.
    13→- Owner isolation: every query and route is owner-scoped.
    14→- Local access: loopback and Host are not identity, since containers reach host listeners. Every local `/api` request needs the owner key from `NOD_DATA_ROOT/access-key` (a cookie set from the printed `#access=` link, or the desktop header); only verified webhooks, OAuth callbacks with one well-formed state, the key exchange and the privacy notice go without it. Never mount the data root or pass the key to a container or prompt.

    16→## Model policy
    17→
    18→- Progress follows the shared rule in `src/shared/conversation-style.ts` in chat, tasks, compact prompts and the observer. Report a result only when the owner can use it now, a change affects their next step or they need to decide. Claims about created, updated or completed work need a confirmed tool result and an inspectable output. Routine checks and private record changes stay quiet. Spending check-ins state the cost and what continuing would do; include completed work only when useful for that decision and inspectable.
    19→- Most confirmation wording and action labels, and channel handoff text, come from the selected model or its text companion through `src/server/communication.ts`. Recent owner messages supply language context, never action facts. The writer receives the saved action, arguments, sanitized account and target details, and task or schedule context. A separate request to the same model checks its question and label against the same frozen facts. One repair can correct a rejected draft; an invalid or rejected second attempt stops before an approval is saved. Questions describe the outcome and material facts in the owner's language, without raw tool data, browser references or page dumps. For permanent Gmail deletion, the server writes a fixed English question and action label naming the permanent effect and verified target without a wording-model request. Hidden values require an incomplete-description notice. Private links and Unicode direction controls are removed or made visible, while model-written Markdown is escaped and link-like text is formatted as code, before the separate review. The label is stored in `approvals.title`, separate from executable arguments, and never grants authority. Old approvals use their existing action label. Approvals recheck the turn before saving. Before asking about a permanent Gmail deletion, the server checks read authority, verifies the exact message ID and identifying metadata, and binds the selected account; a confirmed deletion rechecks that binding before execution.
    20→- Pi does not ask before app actions, sign-ins, bookings or payments; the trust check and payment approval ask the owner when their words don't cover an action. Pi asks only when the account, target or action is unclear.
    21→- The chat UI adds no model-cost labels or action receipts to messages. Costs and Nod's recorded actions (app actions, committed browser steps, local files, its own settings changes, sign-ins and card submissions) remain in Usage: each row names the request and what it changed and opens its step log (model calls, actions with targets and reasons, other tools, notes, helpers and the reply), Export downloads the full log as CSV, and Nod reads its actions with `usage_get` to answer what it did; recurring schedules show a projected monthly cost based on recent run costs and schedule frequency; a schedule with no finished runs uses the owner's recent schedule runs, else their recent finished turns, else the spend of the turn that set it up, and Nod states the projection when it creates a recurring schedule or changes its timing. Usage shows background spend (sessions not started by an owner message, plus spend with no turn grouped by kind) separately.
    22→- The notification rule is empty until the owner asks for updates. After the owner approves an action from background work that will come up again, Pi offers once, at the end of its result, to add it to the rule; after one in chat or a task, it offers once to add it to the owner's rules.
    23→- Automatic preparation starts off for new profiles and preserves existing choices. App events, source change tokens and due matters feed one shared observer. Generic apps have no periodic model check. Code collects source pages within 12 page reads and a 96 KB soft bound, then compares source versions after a normal Trust read and skips unchanged successful assessments. The selected model assesses changed batches. There is no separate observer model selector. Outside work starts a normal task. Source reviews, email privacy checks, the observer and its tasks share a $5 monthly preparation allowance by default. The ledger reserves each model request before dispatch under an owner lock and keeps unresolved reservations. Unknown prices block automatic requests, and while the model for Nod's own work or the chat connection's smaller model has no price, the observer, background inbox polling and background email checks don't start; Settings → Notifications names that model. Owner requests, schedules and owner-started tasks keep their normal limits. Its turns use `turns.proactive=true`, `read_source`, `proactive_issue`, and read-only personal context. It starts a separate keyed task for an outside action, question, or wait. The task uses normal tools with `proactive=false` and keeps event authority and every normal Trust check. Its generated brief grants no permission. Only a spending check-in can pause the observer with `ask_user`. It never asks the owner about a read and skips the source instead. After the connection service answers 429 or 503, the provider holds one in-memory wait for the whole install (its `Retry-After`, at most 15 minutes, or one minute doubling to 30; a successful request started after the latest refusal resets it, except session creation or deletion); during it, source, discovery, inbox, change-token, scheduled and event-started task reads skip the service and fail like any read failure, `apps` reads in work the owner started still try once, and actions fail before dispatch with the wait time. Before saving, the server re-reads cited records, or for tool reads requires a read from the same turn within two minutes. Matters use a primary record and a hashed stable matter key; resolution holds until the condition changes and dismissal until the condition changes or a new option appears, never for a moved deadline; feedback is not dismissal. A source signal carries the app's event text, up to ten per source, as untrusted data for the next run. Delivery has no message count: the worker offers only work worth an interruption, and the server enforces one nudge per matter (again only on a material evidence change), quiet hours (a high-impact nudge with strong evidence whose deadline comes before they end goes out at once), snooze and `proactivePaused`, which also stops Gmail inbox polling (webhook events keep only a content-free summary) and the planned checks of observer-started tasks; owner-created schedules and tasks keep running. Due matters whose deadline is not before quiet hours end wait for that time. A task the observer starts during quiet hours begins when they end: `turns.start_after` holds its first turn. A nudge states the concrete finding and why it needs attention now. It asks a next-step question only when that helps the owner decide and fits their requested format. Every nudge includes a server-derived link to its saved result. The owner-scoped page shows the latest draft, unknowns and sources without a model turn, and refuses removed or replaced source bindings. The owner answers in words: `prepared_list` reads a draft, and `prepared_update` changes one only in a turn started by an owner message. The observer uses the normal session check-in and monthly spending limit. Source signals stay saved while it waits for a spending reply. Explicit account removal deletes source-linked private work in the removal transaction; temporary loss does not. See `docs/src/content/docs/how-it-works/proactivity.md`.
    24→- Onboarding starts workspace preparation when the owner leaves the welcome screen (the desktop app starts its computer and database when the welcome screen opens, and its engine then too only on a profile with no saved keys; otherwise the engine and key unlock wait for **Get started**. After **Get started**, the setup window shows loading progress until the database-backed engine is ready. Onboarding then opens without waiting for account discovery, the workspace or the browser; completing onboarding waits for those local services), connects email optionally, asks optional About you questions, asks for a model only when none works, asks about conversation traces and says that usage data, on by default for new owners, is shared, then offers an optional Join us step. About you saves fixed choices, including multiple roles and a conditional who-for answer, plus optional own words through `memory.restate` as one stated `about/onboarding` note, which first-chat task cards read; analytics store only fixed choices in events and explicitly set those bounded answers on the installation’s PostHog person profile while usage sharing is enabled, even without an email. When the updates email is available and usage sharing is on, Join us offers an optional email field for updates about Nod and other n8n products and an unchecked consent box that names n8n GmbH, the link to usage data and how to withdraw. Submitting both while sharing is enabled sets the PostHog `email` person property under the same installation ID. Email submissions with the updates checkbox ticked while usage sharing is on go through the internal n8n onboarding webhook to record an unverified signup request on a new or existing Customer.io Labs profile. Submission sends no email immediately. Discord and forum are secondary in Join us and linked from Settings → General. With a confirmed email connection, first-task discovery starts when the owner leaves About you, after its answers are saved. The first chat opens with a short greeting, then learned and common task cards and a follow-up line saying the owner can ask for more ideas; when apps whose notification senders appeared in the discovery sample aren't connected, the line names up to three of them (sender addresses only, matched to a fixed list in `src/shared/sender-apps.ts`, skipping the owner's own email domain and hidden account-access email; only app slugs are kept, never mail content). The card message text the model sees includes that line. Asking for more ideas is a normal owner message. Pi gives useful ideas in that turn from stated goals, current context or a small permitted read of a relevant connected app. It offers concrete tasks, recommends one and names its result and any input needed. New connections are optional, not a condition for receiving ideas. With no apps, empty sources or failed reads, it suggests work from supplied text, files or public sources without inventing account contents. Suggestions start no work; a clear owner selection starts the chosen task through normal checks. Detailed tours and access explanations remain valid requests. No setup interview blocks completion. The first stored chat introduction offers notifications without enabling them. Permission and opt-in require the owner to select Enable notifications or change Settings. Existing notification choices are preserved. Operating-system permission controls delivery and does not authorize notification rules or app monitoring. First-chat task cards are prepared without a turn from existing setup answers and small samples from connected tools. Discovery selects up to three schema-validated reads per account (for email, one of them a sender and subject listing of about 50 recent messages), passes every read through the selected model's strict read-only check with the owner's rules, and revalidates the exact account binding before reads and publication. Unknown actions, drafts and writes cannot run. Account-access email and secret fields are removed before observations reach the suggestion model. A temporary brief informs one immediate and two ongoing cards; the brief is not saved to memory. Discovery stops when the owner sends a message, the app closes or its deadline expires. Cards are checked for shape, connected source and distinct titles; one repair is allowed before invalid cards are replaced with fixed ones. Selecting a card sends exactly its visible title as a normal owner message.
